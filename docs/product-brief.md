# RoleBerry product brief

Prepared as a handoff for marketing.

Every claim in section 2 was read out of the source at commit `15ec25a` (branch `auth`) and
independently re-checked by a second pass. Live-site claims were checked against
https://roleberry.app on 26 August 2026. Anything that could not be confirmed is in section 3,
not section 2. File references are `path:line` so any claim here can be traced back to code.

---

## 1. WHAT IT IS

RoleBerry rewrites a CV against a specific job posting.

A person signs in with Google, enters their career history once, and it is saved to their
account. After that, each application takes one step: paste the job posting, press Optimize,
and get back a CV rewritten for that posting, downloadable as a PDF. A cover letter can be
produced in the same action.

The product is a single-page React app (`components/CVOptimizer.jsx`, 1,930 lines) talking to
three POST endpoints (`server/index.js:44-50`). Profiles are stored per user in Firestore
(`services/auth.js:60-87`). Text is generated by `google/gemini-2.5-flash` through OpenRouter.

What it is not, as currently built: there is no billing, no team or sharing model, no admin
surface, and no per-user quota. Every signed-in Google account draws on the operator's single
API key. It is built as a tool for one operator and the people they hand it to.

The product is named **RoleBerry** on every screen, in the browser tab and in the downloaded
filename. It previously carried two names (TailorCV on the sign-in screen, RoleReady
everywhere else); that was resolved on 26 August 2026. Two internal storage identifiers still
use the old string and were deliberately left alone; see section 5.

## 2. SHIPPED FEATURES

Everything in this section exists in the repository and was traced end to end. The right-hand
note says whether it is also on the live site today. The live bundle is 8 days old, so it is
behind the repository by one feature (browser OCR); see section 3.

### Getting in

**Google sign-in, required for everything.** The app renders a sign-in screen instead of
itself when there is no user; there is no other way in and no email or password option.
`components/CVOptimizer.jsx:1459`, `components/Auth.jsx:169-193`, `services/auth.js:5-27`.
*Live: yes.*

**Every API call requires a verified token.** The three endpoints each verify a Firebase ID
token (RS256 signature against Google's certificates, plus expiry, audience and issuer checks)
before doing any work. `server/core/firebaseAuth.js:29-101`, called at
`optimizeHandler.js:150`, `pdfHandler.js:288`, `aiDetectHandler.js:5`.
*Live: yes, verified by request. An unauthenticated POST to https://roleberry.app/api/optimize
returns `401 {"error":"Authentication required"}`.*

**Profile is per account and is cleared on sign-out.** The profile loads from Firestore on
sign-in and all derived state is wiped on sign-out or when a signed-in account has nothing
stored, so a second person signing in on the same browser does not see the first person's
data. `components/CVOptimizer.jsx:419-449`, `:395-416`, `services/auth.js:74-87`.
*Live: yes.*

### Building the profile

**Setup page with seven sections.** Import, Personal, Links, Skills, Experience, Education,
Certifications. `components/CVOptimizer.jsx:903-1456`, section list at `:48-56`.
*Live: yes.*

**Import from an existing PDF CV.** Upload a PDF and the whole setup form is filled in: name,
contact, links, skills grouped into categories, roles with their bullet points, education and
certifications. Years of experience are computed from the parsed date ranges.
`components/CVOptimizer.jsx:480-540`, `:259-312`, `server/core/pdfHandler.js:287-338`.
*Live: yes.*

**Browser-side OCR for scanned CVs.** When the server rejects a PDF as image-based, the
browser renders up to 5 pages to a canvas and runs Tesseract on them locally, showing
"Reading page N of M", then sends the recognised text instead of the file. The scanned file
itself never leaves the machine. `services/browserOcr.js:84-131`,
`components/CVOptimizer.jsx:494-512`, `server/core/pdfHandler.js:294-302`.
*Live: **no**. Confirmed absent from the deployed bundle (zero occurrences of `tesseract`).*

**OCR assets are fetched ahead of time.** For a signed-in user who has not built a profile

begin with a multi-megabyte wait. Skipped on data-saver or 2G connections.
`components/CVOptimizer.jsx:344-347`, `services/browserOcr.js:37-78`.
*Live: no, same as above.*

**Skills entered as chips.** Commit on Enter, comma or blur; a pasted comma-separated list
splits into separate chips; Backspace on an empty field removes the last one.
`components/CVOptimizer.jsx:1239-1253`, `:946-963`. *Live: yes.*

**Skill groups and roles collapse.** A collapsed role still shows title, company, dates and
how many achievements it holds. `components/CVOptimizer.jsx:965-969`, `:1311-1323`.
*Live: yes.*

**Section rail with progress.** A sticky left rail lists the seven sections, highlights
whichever is on screen as you scroll, marks each one complete or not with an item count, and
shows "N of 7 complete". `components/CVOptimizer.jsx:1000-1044`, `:350-366`, `:904-939`.
Desktop only; see section 5. *Live: yes.*

**The main screen is gated until the profile is usable.** Until there is a name, one skill

`components/CVOptimizer.jsx:1546-1556`, `:314-318`. *Live: yes.*

### Generating

**Paste a job posting, press Optimize.** The posting and the stored profile go to
`/api/optimize`, which returns a rewritten summary, a reordered and rewritten skills block,
and rewritten bullet points per role, plus the keywords it used.
`components/CVOptimizer.jsx:824-900`, `server/core/optimizeHandler.js:149-572`.
*Live: yes.*

**The skills block is corrected server-side, not trusted as returned.** Duplicate skills are
removed case-insensitively, categories are capped at 9 and items at 9 per category, skills
taken from the job description are ordered ahead of the rest, and categories are sorted into a
fixed order. `server/cvValidation.js:1-77`, applied at `optimizeHandler.js:399-400`.
*Live: yes.*

**Each role keeps its own header.** Title, company, location and dates are re-attached from
the submitted profile by role ID rather than being taken from the model output.
`server/core/optimizeHandler.js:408-448`, `components/CVOptimizer.jsx:29-44`. *Live: yes.*

**Formatted preview.** The result is rendered into a complete HTML document and shown in an
iframe, so the layout is the same on every run regardless of how the model formatted its
output. `src/templateRenderer.js:57-192`, `components/CVOptimizer.jsx:1717-1735`.
Note: this preview is not the same renderer that produces the downloaded CV PDF; see section 5.
*Live: yes.*

**Optional cover letter.** A toggle above the Optimize button adds a cover letter, generated
by a second model call. The preference is remembered between visits. If the letter fails, the
CV is still returned. `server/core/optimizeHandler.js:86-134`, `:536-544`,
`components/CVOptimizer.jsx:1576-1599`, `:183`. *Live: yes.*

**Switch between the two documents.** Once a letter exists, a tab control switches the
preview, the heading and the download button between CV and cover letter.
`components/CVOptimizer.jsx:1657-1696`. *Live: yes.*

**Copy the cover letter.** One button copies the letter text, with a fallback path for
browsers or origins where the clipboard API is unavailable, and confirms for two seconds.
`components/CVOptimizer.jsx:789-822`, `:1701-1714`. *Live: yes.*

**Optional per-application folders (Chromium only, off by default).** With folder management

**Every download failure falls back and says what happened.** If the folder cannot be opened,

`components/CVOptimizer.jsx:641-658`, `:1770-1789`. *Live: yes.*

## 3. NOT SHIPPED

Do not put any of this in marketing material. Several items exist as code or as claims in the
repository's own documentation, which is what makes them worth listing.

### The live site is behind the repository

The last production deployment is 8 days old (`vercel ls roleberry`). Deployments are made
from the working tree rather than from a git commit, so the exact contents of the live build
cannot be read off the repository history. What can be checked, and was: browser OCR is not in
the live bundle. Cover letters, the text-based PDF export, folder management and the
authentication gate are. **Anything written about OCR would be describing a feature the public
site does not have today.**

### Documented but not real

**Server-side OCR of scanned PDFs.** `PDF_EXTRACTION_CONFIG.md:8` and `:59-83` describe this
in detail, including timings and memory figures per hosting platform. The function ignores its
arguments and throws immediately (`server/core/PDFTextExtractor.js:89-93`). The scanned-CV
case is handled in the browser instead, and only in the repository, not live. The
`PDF_OCR_DPI` setting is read, passed along, and reaches only the code that throws.

**README claims that contradict the product.** `README.md:73-74` says scanned PDFs are not
supported. `README.md:78` describes the download as an HTML file to print yourself, which the
text PDF export replaced. `README.md:64-81` describes using the app with no mention that a
Google account is mandatory. `README.md:164-165` refers to a licence; there is no LICENSE file
in the repository.

**Stale copy in the README.** The in-app copy was corrected on 26 August 2026 (the import hint
and the Tips panel entry both describe current behaviour now). The README statements above
have not been.

### Built but unreachable

**Firebase Functions as a hosting target.** Configured but cannot run as deployed, for two
independent reasons: `firebase.json:3` uploads only the `functions` directory while
`functions/index.js:13,16` imports from `../server/core/`, outside that directory; and the
hosting rewrite sends `/api/**` to a function that registers bare `/optimize` and
`/process-pdf` (`functions/index.js:55,61`). It is also missing the `/detect-ai` route, and its
request body limit is 1 MB against the 4 MB the OCR path needs. Two hosting targets work:
local Express and Vercel.

**The loading-animation showcase.** 29 animations in `components/LoadingShowcase.jsx` (1,071
lines), reachable only through a separate dev server on port 5174. It is not in the production
build and the hosting rewrites make it unreachable on both hosts. The real loading indicator is
a plain spinner (`components/CVOptimizer.jsx:1605-1609`).

**A `/health` endpoint.** Exists only on the Firebase target, which cannot run. Neither working
host has one.

### Partly built

**Minimum sizes on the skills block.** The lower bounds (6 categories, 3 items each) are
accepted as settings and never enforced; nothing is added to reach them, and the code says so
(`server/cvValidation.js:30`). The user is warned; the CV is not corrected. `README.md:19`
presents these bounds as a property of the output.

### Absent entirely

- **Automated tests.** None. No test file and no test script in either `package.json`.
- **Rate limiting or per-user quotas.** None. Authentication is the only gate, so any signed-in
  Google account can make unlimited model calls (`server/index.js:19-39`).
- **Continuous integration or automated deployment.** No `.github` directory; deployment is
  manual.
- **Deep links, browser back/forward, shareable URLs.** All three screens are one component
  switching on a state string (`components/CVOptimizer.jsx:169`). No router is installed.
- **Saved history of past CVs.** Each run replaces the last. The only persisted data is the
  profile.
- **A licence file.**

### Dead weight in the repository

Worth knowing about because it inflates any size or dependency claim: `canvas` and
`@vercel/speed-insights` are installed and imported nowhere (`package.json:19,21`);
`eng.traineddata` (5,199,098 bytes) is committed at the root and referenced by nothing;
`scripts/patch-pdfjs.js` is a byte-identical duplicate of the `.cjs` file that is actually
used; four exports in `services/folderManager.js` have no callers; `main.js`,
`showcase.html`, `Untitled-1.html` and `static-cv-template.html` are unreferenced. The four
tiles on the sign-in screen (Smart Keywords, Job Matching, Clean Design, Save Templates) are
decoration with no behaviour behind them (`components/CVOptimizer.jsx:1481-1498`), and
"Save Templates" describes something the product does not do.

## 4. HOW IT WORKS

**Sign in.** Google sign-in through Firebase. The profile lives at `users/{uid}` in Firestore
as two JSON documents, written from the browser (`services/auth.js:60-87`). There is no
server-side persistence endpoint at all.

**Build the profile, once.** Either by typing it into the seven-section setup form, or by
uploading an existing PDF CV. On upload, the file goes to `/api/process-pdf`, which extracts
text from up to 5 pages, then makes a model call that returns two labelled JSON objects
(skills and experience; personal details). Those are parsed by a brace-aware scanner that
survives code fences and commentary around the JSON (`server/core/pdfHandler.js:119-149`) and
written into every form field.

**If the PDF is a scan.** The server classifies a PDF by sampling its first 3 pages: under 50
characters of text and it is treated as image-based and refused. The browser catches that
refusal, renders up to 5 pages to a canvas at 2x scale, runs Tesseract locally, and posts the
recognised text back to the same endpoint, which skips its own extraction
(`services/browserOcr.js:84-131`, `server/core/pdfHandler.js:294-302`). The scanned file is
never uploaded. Repository only, not live.

**Generate.** The job posting plus both profile documents go to `/api/optimize`. One model call
returns a single JSON object with six keys: summary, skills, experience, keywords used, overlap
skills, and the company name. The server then:

1. parses it, stripping code fences (`optimizeHandler.js:329-352`);
2. removes duplicate skills, caps categories and items at 9, orders job-description skills
   first (`cvValidation.js:1-77`);
3. re-attaches each role's real title, company and dates by role ID (`:408-448`);
4. renders a markdown copy of the CV (`server/cvRenderer.js:1-82`);
5. filters the keyword list down to terms that actually appear in the output (`:511-527`);
6. sets a warning flag if the result missed the size or job-description targets (`:470-473`).

**Cover letter.** A separate model call with a trimmed profile (top 3 roles, 4 achievements
each, 25 skills). The greeting and the sign-off are assembled in code rather than asked of the
model (`optimizeHandler.js:131-133`). A failure here is caught and returns an empty letter, so
it cannot cost the user their CV.

**Show and download.** The structured result is rendered to a full HTML document and shown in
an iframe. The CV download is drawn separately with PDF text primitives (`src/cvPdf.js`). With
folder management on, the file is written into a numbered per-application subfolder and read
back to confirm it is not empty; every failure path falls back to an ordinary download with an
explanatory notice.

**Model and hosting.** `google/gemini-2.5-flash` through OpenRouter, three separate calls (CV
at 4,000 tokens, cover letter at 900, PDF import at 4,000). Note that if the environment
variables are unset the code silently falls back to OpenAI's `gpt-4o-mini`
(`optimizeHandler.js:142-143`), which is not the model the prompts were written against.
Hosting is Vercel; the same handler modules serve local Express during development.

## 5. CONSTRAINTS AND LIMITS

**Browser support.** Per-application folders require the File System Access API, which is
Chromium only. The toggle is disabled and labelled "Not supported in this browser" elsewhere
(`services/folderManager.js:67`, `components/Auth.jsx:126`). Everything else works in any
modern browser. OCR additionally needs WebAssembly and a visible tab.

**Page limits.** Both PDF paths read at most 5 pages, and classification looks only at the
first 3 (`server/core/pdfHandler.js:22-23`, `services/browserOcr.js:21`). A CV whose first
three pages are a scanned cover sheet is classified as image-based.

**OCR is English only.** The worker is created for English with no other language configured
(`services/browserOcr.js:60`). In measured runs it read a real CV at 92-93% confidence,
roughly 1.2 seconds per page, with predictable confusions on capital I and lowercase L: `(IaC)`
read as `(laC)`, `GitLab-CI` as `GitLab-Cl`.

**OCR needs the public internet.** Nothing self-hosts the OCR engine or language data; both are
fetched from a third-party CDN at run time. It will not work offline, behind a locked-down
network, or under a strict content security policy.

**The preview is not the downloaded file.** The preview is HTML in one font; both PDFs are
drawn by a different engine in another. Same content and same section order, but spacing, fonts
and page breaks will not match exactly. The preview should not be presented as a preview of the
printed file. This now applies to the cover letter too, which moved onto the text renderer on
26 August 2026.

**Renaming the storage identifiers costs one folder re-pick.** The IndexedDB database name
and the directory-picker id in `services/folderManager.js:1,96` were renamed to `roleberry` on
14 October 2026. Both are invisible to users, but the change discards any saved folder handle
and resets the browser's memory of which directory was picked, so anyone using folder
management has to choose their folder once more. No migration was written; with the current
user count that was judged cheaper than the code.

**The iframes are not sandboxed.** No `sandbox` attribute is set on either preview iframe
(verified: the word appears nowhere in the components, config or HTML). What protects the
preview is that values are escaped and non-http links are dropped in the renderer
(`src/templateRenderer.js:59-76`), not isolation. Do not describe the preview as sandboxed.

**The job-description share statistic is self-reported.** The headline "share of skills taken
from the job posting" is the model's own label on its own output. It is never checked against
the text of the job posting. The code says so in a comment (`server/cvValidation.js:41-46`).
It drives a user-visible percentage and a warning banner. It should not be quoted as a measured
accuracy figure.

**Input caps, enforced with a browser alert.** Job description 10,000 characters, profile
documents 20,000 and 10,000 (`components/CVOptimizer.jsx:829`). Exceeding one produces a
blocking alert box, and most error handling on the main flow works the same way rather than
showing an in-page message.

**Upload ceiling is lower in production than in code.** The code allows 10 MB
(`server/core/pdfHandler.js:33`), but Vercel caps serverless request bodies at 4.5 MB, so the
platform limit is what applies on the live site. This is recorded nowhere in the repository.

**Function durations exceed the free tier.** `vercel.json` requests 300 seconds for the
optimize and PDF routes. The Vercel Hobby plan caps at 60 seconds, so those values need a paid
plan to apply as written.

**Nothing prevents cost overruns.** No rate limit, no quota, no timeout on any outbound model
call (`optimizeHandler.js:109,290`). One shared API key serves every signed-in account.

**AI detection fails silently.** If its API key is unset the endpoint returns an error, the
client swallows it, and the score simply never appears with no explanation to the user
(`aiDetectHandler.js:14-17`, `components/CVOptimizer.jsx:876`).

**Desktop-only interface elements.** The setup section rail, its completion dots and the
progress meter are hidden below the large breakpoint, as is the collapsing job-description
column. On a phone the setup page has a sticky bar with a progress line and Save, and nothing
else.

**Dark mode is not remembered.** It resets to light on every reload
(`components/CVOptimizer.jsx:323`), and it cannot be reached at all before signing in.

**A dependency the export depends on is undeclared.** `src/cvPdf.js:1` imports `jspdf`, which
is not listed in `package.json`; it installs only as a sub-dependency of `html2pdf.js`. If that
package changes its dependencies, the PDF export breaks.

**Password-protected PDFs** produce a generic "please ensure the PDF contains readable text"
message rather than being identified as locked.

**Bundle size.** The main JavaScript file is 1.41 MB (382 kB compressed), plus a 1.13 MB PDF
worker, before any OCR assets are fetched. The build emits a large-chunk warning.

## 8. OPEN QUESTIONS

These need answers from you before marketing copy is written. They are decisions, not gaps I
can close by reading more code.

1. **Is RoleBerry the final name?** Settled: every screen, the browser tab, the download
   filename and the storage identifiers say RoleBerry, and the domain is `roleberry.app`.
   Nothing has been checked for trademark conflicts. The Firebase project id is still
   `roleready-d7295` and cannot be renamed without creating a new project and migrating every
   user document.

2. **Should the site be redeployed before this goes out?** The live build is 8 days old and
   does not include browser OCR. Everything else in section 2 is live. If OCR is part of the
   story, the deployment has to come first.

3. **How should scanned-CV support be described?** The in-app hint was corrected on
   26 August 2026 and now reads "PDFs up to 10MB, including scans". The README still says
   scanned PDFs are unsupported. Note the feature is still not deployed, so the corrected hint
   currently promises something the live site cannot do; the deploy in question 2 has to land
   first.

4. **Who is this for?** There is no billing, no quota and one shared API key, so the current
   build cannot absorb open sign-ups without a cost ceiling. Positioning it as a personal tool,
   an invite-only tool, or a product with accounts is a decision that changes both the copy and
   what has to be built first.

5. **What can be claimed about privacy?** The defensible statement is narrow and true: scanned
   files are read in the browser and never uploaded. Text-based PDFs, the job posting and the
   profile all do go to the server and on to a third-party model provider, and profiles are
   stored in Firestore. Confirm how far you want to go here, because the strong version of the
   claim is not true.

6. **Is the job-description share figure usable at all?** It is prominent in the UI and it
   measures nothing. Options: drop it from marketing and keep it as an internal signal, or
   change it to something actually measured against the posting text.
